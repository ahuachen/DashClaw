## Requirements Closed

- **BUG-03**: The founder is viewing his own DashClaw instance as `role='member'` instead of `role='admin'`.
  - **Root cause**: `app/lib/auth.js:108` hardcoded `role: 'member'` in the NextAuth `signIn` callback's new-user INSERT, with no first-user detection. Every OAuth signup became a non-admin, including the instance operator.
  - **Not caused by `3dcb43dc`**: the Lief LAN/CSP port was cleared as not-the-cause during diagnosis (see `01.5-BUG03-DIAGNOSIS.md`). `3dcb43dc` changed the local-admin session cookie's orgId, not the NextAuth user role.

## What Changed

### `app/lib/auth.js` (modified)

Added first-user detection inside the `signIn` callback's new-user branch. Before the INSERT, run `SELECT COUNT(*) FROM users` — if 0, this is the first user and gets `role='admin'`; otherwise `'member'` (preserving existing behavior). The INSERT now uses the computed `newUserRole` variable instead of hardcoding `'member'`.

An inline comment documents the race window (two simultaneous first signups could both be promoted — accepted as preferable to zero admins on a single-operator self-hosted deploy).

### `scripts/promote-founder-to-admin.mjs` (new, 90 lines)

One-off retroactive promotion script for existing users who were created as `member` before this fix landed. Idempotent: re-running against an already-admin user is a no-op. Takes email as CLI arg. Uses the existing `getSql()` from `app/lib/db.js`. Follows the pattern of `scripts/migrate-api-keys-compat.mjs` (added by Plan 01-01's executor).

Usage:
```
node scripts/promote-founder-to-admin.mjs <your-email>
```

### `__tests__/unit/bootstrap-first-user-admin.test.js` (new, ~130 lines, 4 tests, all passing)

Regression test suite covering:
1. **First user (count=0) → `role='admin'`** — promotes correctly
2. **Subsequent user (count=5) → `role='member'`** — does NOT promote
3. **Existing user re-login → UPDATE branch** — no COUNT or INSERT calls, role unchanged
4. **Edge case: count field missing / null** — optional chaining treats as first user (safer failure mode)

Uses the project's established Vitest pattern from `__tests__/unit/guard.route.test.js`: `vi.hoisted` for mocks, `vi.mock('@/lib/db.js')` to intercept `getSql()`, and `mockSql.mock.calls` inspection to verify the INSERT was called with the correct role value.

## Deferred — Noticed Out of Scope

Flagging findings that were noticed during diagnosis but are NOT fixed in this plan. Do not fix these without explicit approval — they belong in separate plans:

1. **Local-admin password dual-session gap**: `app/api/auth/local/route.js` creates a `dashclaw-local-session` cookie with hardcoded `role='admin'`, but `useSession()` from NextAuth does NOT read this cookie. So even a local-admin user (the no-OAuth self-host path) would see the READ-ONLY banner on `/approvals` because the approvals page only checks `session?.user?.role`. This means the local-password path is *also* affected by BUG-03, via a different mechanism. Fix would require either (a) bridging the two session systems, (b) making the approvals page check both, or (c) refactoring local auth to go through NextAuth as a custom provider. **Tracked as a follow-up bug — likely BUG-03b or a separate phase.**
2. **Silent failure anti-pattern in `signIn` catch block** (`app/lib/auth.js:112-116`): if the DB upsert fails, the callback returns `true` (allow login) anyway. This is a "graceful degradation" that violates CLAUDE.md's no-silent-failures rule. Not in scope for BUG-03 but worth flagging as tech debt.
3. **`role` column may be unconstrained text**: diagnosis did not verify whether `users.role` is a Postgres enum, a CHECK constraint, or a free text column. Making it an enum would prevent future typos ("admin" vs "Admin" vs "administrator"). Not in scope.
4. **`scripts/promote-founder-to-admin.mjs` was not run** — it's authored and committed but has not been executed against the live database. T4 (handoff to Wes) is where Wes runs it with his own email.

## Addendum 2026-04-11: Re-diagnosis after T4 validation

When Wes ran `scripts/promote-founder-to-admin.mjs sandman.uc@gmail.com` during T4, the script output was:

```
User sandman.uc@gmail.com is already admin (id=usr_7ad6e7ee-dd6b-4a66-b5aa-331f3c88c4e3, org=org_5979f05b-c7ce-440f-8a1d-c9b1bcb68cfd). No change.
```

**This invalidated the original diagnosis.** Wes's user record was already `role='admin'` in the DB. The INSERT-hardcodes-member hypothesis documented in `01.5-BUG03-DIAGNOSIS.md` was real in the code, but it was NOT what caused the symptom Wes observed on his specific instance. The auto-promote fix in `707c5636` is still valid for *future* fresh deploys, but it did not fix what Wes was actually experiencing.

Asked Wes to reload `/approvals` and tell me what happened to the banner. He said:

> *"That orange banner only flickers at the start of the reload of the site then it disappears."*

That's the actual bug. **React/Next.js hydration flash:**

1. `/approvals` mounts on the client
2. `useSession()` has not yet resolved the NextAuth JWT — during that window `session` is `undefined` and `status === 'loading'`
3. The component computes `const isAdmin = session?.user?.role === 'admin'` → `undefined === 'admin'` → `false`
4. The conditional `{!isAdmin && <Banner>...</Banner>}` at `app/approvals/page.js:119` renders the orange READ-ONLY banner on first paint
5. ~100-300ms later the session resolves, `isAdmin` becomes `true`, re-render fires, banner disappears

The component was missing a `status !== 'loading'` guard on the banner. It treated *"session is still loading"* and *"session loaded, user is definitively not admin"* as the same state.

### Real fix (commit `760aa727`)

Three-line change to `app/approvals/page.js`:

1. Destructure `status` from `useSession()`
2. Compute `const sessionSettled = sessionStatus !== 'loading';`
3. Gate the banner on `{sessionSettled && !isAdmin && <Banner>...}`

Inline comment explains the bug so future grep'ers understand why the guard exists. Banner's visual design is unchanged — this is a logic fix, not a visual design change, so `.impeccable.md` consultation was not required.

### Lessons from the miss

**Diagnostic discipline failure.** I claimed "hypothesis (a) confirmed" in the diagnosis based on reading `app/lib/auth.js:108` (which does hardcode `role='member'` for new users) without querying the live DB to check whether Wes's specific record actually had that bug. The code was bugged AND Wes's record happened to already be admin from a different historical path — both could be true, and I conflated "the code has this bug" with "this bug is what's affecting you now."

**The live-query step should have come before claiming a confirmed root cause.** If I had queried `SELECT id, email, role, org_id FROM users WHERE email = 'sandman.uc@gmail.com'` during T1, I would have seen `role='admin'` immediately and known the bug was elsewhere. I ran only static code analysis, which showed a plausible bug pattern, and jumped to "confirmed" without verification.

**The fix I shipped is not wasted.** The first-user auto-promote in `707c5636` addresses a real bug pattern in the code — if someone deploys a fresh DashClaw instance today and signs in, they would still become a `member`-only user without the fix. So `707c5636` is the right fix for a real problem; it's just not what Wes had. The bootstrap path has been hardened for future users regardless of whether Wes's specific instance needed it.

**Both fixes should stay.** The hydration-guard fix (`760aa727`) addresses the UX flicker for every user (admin and non-admin alike), and the first-user auto-promote fix (`707c5636`) addresses the role-assignment bug for future deploys.
