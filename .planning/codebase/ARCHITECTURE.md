# Architecture

**Analysis Date:** 2026-03-17

## Pattern Overview

**Overall:** Next.js 15 (App Router) governance runtime with a minimal 7-route API surface and modular extension tier.

**Key Characteristics:**
- **Core-first design**: The runtime enforcement boundary is strictly enforced—only 7 canonical routes in `/api/` (guard, actions, approvals, assumptions, signals, policies, health).
- **Layered governance**: Tier 1 (core), Tier 2 (extensions), Tier 3 (archived legacy).
- **Repository pattern**: All database access is isolated to `app/lib/repositories/*.repository.js` to enforce separation of concerns from route handlers.
- **Multi-tenant by design**: Every route scoped to `orgId` via request headers; all database queries filter by organization.
- **Server-side risk computation**: Guard evaluation engine uses deterministic scoring, not client-side logic.

## Layers

**Presentation Layer:**
- Location: `app/` (all page components and dashboards)
- Contains: `page.js` files, React components, client-side state management
- Depends on: API routes, lib utilities
- Used by: Browser clients, authenticated operators

**API Layer (Tier 1 - Core):**
- Location: `app/api/` (7 canonical routes only)
- Routes: `/guard`, `/actions`, `/approvals`, `/assumptions`, `/signals`, `/policies`, `/health`
- Pattern: Each route has `route.js` that handles GET/POST/PATCH/DELETE
- Responsibility: Request validation, org scoping, delegation to repositories
- Guard by: `npm run governance:boundary:check` prevents new routes here

**API Layer (Infrastructure):**
- Routes: `/api/cron/*` (scheduled tasks), `/api/integrations/health`, `/api/docs/raw`
- Purpose: Background jobs, health checks, documentation generation
- Not governed by boundary check—helper routes only

**API Layer (Tier 2 - Extensions):**
- Location: `app/(extensions)/` (not enforced by boundary)
- Routes: `/api/compliance/*`, `/api/drift/*`, `/api/evaluations/*`, `/api/scoring/*`
- Purpose: Modular intelligence features (audit, metrics, LLM scoring)
- Consumed by: `app/compliance/`, `app/drift/`, `app/evaluations/`, `app/scoring/` pages

**API Layer (Tier 3 - Archived):**
- Location: `app/api/_archive/` (quarantined legacy)
- Routes: `/api/agents/*`, `/api/messages/*`, `/api/webhooks/*` (partial)
- Reason: Platform features from "Agent Workspace" era; not core governance

**Business Logic Layer:**
- Location: `app/lib/` (shared evaluation, validation, domain logic)
- Key files:
  - `guard.js` — Risk scoring and policy evaluation engine
  - `signals.js` — Anomaly detection (autonomy spikes, stale loops, etc)
  - `validate.js` — Input validation schemas (action, loop, assumption)
  - `events.js` — Internal event publishing for org-scoped broadcasts
  - `embeddings.js` — Vector generation for semantic search
  - `security.js` — Sensitive data scanning and redaction
- Depends on: Database connection, external APIs (LLM, Slack, Discord)

**Data Access Layer:**
- Location: `app/lib/repositories/` (all database queries live here)
- Pattern: One repository per domain entity (`actions.repository.js`, `agents.repository.js`, etc)
- All repositories accept `sql` (Neon/Postgres client) as first parameter
- No direct SQL in route handlers—only repository calls
- Key repositories:
  - `actions.repository.js` — Action lifecycle (create, update, list, trace)
  - `assumptions.repository.js` — Reasoning integrity
  - `settings.repository.js` — Org configuration
  - `learningLoop.repository.js` — Learning episodes and recommendations
  - `integration-health.repository.js` — Credential validation results

**Database Layer:**
- Location: `schema/schema.js` (Drizzle ORM schema definitions)
- Driver: Neon (serverless) or Postgres TCP
- Connection pooling: Managed by `app/lib/db.js` (global singleton to survive HMR)
- Migrations: `drizzle/` directory (auto-generated by drizzle-kit)
- Key tables:
  - `organizations` — Tenant boundaries
  - `users` — Team members
  - `action_records` — Governance audit trail
  - `guard_policies` — Policy rules
  - `assumptions` — Reasoning records
  - `guard_decisions` — Guard evaluation history

**SDK Layer:**
- Location: `sdk/dashclaw.js` (stable v2 client)
- Surface: 5 core methods (guard, createAction, updateOutcome, recordAssumption, waitForApproval)
- Pattern: HTTP client wrapping the 7 core routes
- Error types: `GuardBlockedError`, `ApprovalDeniedError` for explicit governance failures

## Data Flow

**Governance Loop (Happy Path):**

1. Agent calls `dashclaw.guard(context)` → POST `/api/guard`
2. Guard evaluates policies + computes risk score → returns `{decision, action_id, reason}`
3. If `block` → throw `GuardBlockedError`, operation stops
4. If `allow` or `require_approval` → agent proceeds
5. Agent calls `dashclaw.createAction(action)` → POST `/api/actions`
6. Action record persists to `action_records` table
7. Agent executes the action in real world
8. Agent calls `dashclaw.updateOutcome(id, outcome)` → PATCH `/api/actions/:id`
9. Outcome persists; status transitions to `completed|failed|cancelled`

**Signals Flow (Background):**

1. Cron triggers `/api/cron/signals` every 5 minutes
2. `computeSignals(orgId, null, sql)` scans recent actions
3. Detects: autonomy spikes (>10 actions/hour), stale loops (>48h open), repeated failures (3+ in 24h), etc
4. Publishes event via `publishOrgEvent(EVENTS.SIGNAL_DETECTED, ...)`
5. Subscribers notified via notification adapters (Slack, Discord, Email)

**Human Approval Flow:**

1. Guard returns `decision: 'require_approval'`
2. Agent polls `/api/approvals/[actionId]` or calls `waitForApproval(actionId)`
3. Human visits `/approvals` page, reviews action
4. Human POSTs decision to `/api/approvals/[actionId]` → records approval in `action_records.approved_by`
5. Agent's poll resolves; operation proceeds or is rejected

**State Management:**

- **Request-scoped**: `orgId`, `userId`, `role` extracted from headers/session in every route
- **Database-scoped**: All queries filter by `org_id` (enforced at repository level)
- **Client state**: React hooks in page components (useState, useCallback)
- **Global singleton**: `globalThis.__dashclaw_sql` for database connection (survives Next.js HMR)
- **Event publishing**: In-memory subscribers for org-scoped events (`EVENTS` constants)

## Key Abstractions

**Guard Decision:**
- Purpose: Encapsulate policy evaluation result
- Location: Returned by `/api/guard`, stored in `guard_decisions` table
- Fields: `decision` (allow/warn/block/require_approval), `risk_score`, `reasons[]`, `warnings[]`, `matched_policies[]`
- Pattern: Computed server-side; client receives decision only

**Action Record:**
- Purpose: Immutable audit trail of agent operations
- Schema: `action_records` table (action_id, agent_id, org_id, declared_goal, status, outcome)
- Lifecycle: Created via `createActionRecord()`, updated via `PATCH /api/actions/:id`
- Versioning: No mutations after completion; each status transition is appended to history

**Signal (Anomaly):**
- Purpose: Risk indicator computed from aggregate action patterns
- Types: 7 signal types (autonomy spikes, stale loops, repeated failures, assumption drift, etc)
- Location: `computeSignals()` returns array; each item has `type`, `severity`, `agents[]`
- Delivery: Via notification adapters (Slack webhook, Discord, Email) when triggered

**Assumption:**
- Purpose: Record reasoning basis for agent decisions
- Schema: `assumptions` table (assumption_id, action_id, assumption, validated, invalidated)
- Lifecycle: `recordAssumption()` at decision time; humans later validate/invalidate
- Pattern: Linked to action via `action_id`; enables causal reasoning

**Integration Health:**
- Purpose: Credential validation for external API providers
- Scope: Per organization, per provider (OpenAI, Anthropic, Slack, etc)
- Check: `integration-health.js` calls provider APIs with stored credentials
- Schedule: Runs every 6 hours via `/api/cron/integration-health`

## Entry Points

**HTTP Entry Points:**

**`app/api/guard/route.js`:**
- Triggers: Agent calls SDK `guard(context)` method
- Request: POST with action_type, agent_id, systems_touched, reversible, declared_goal
- Response: `{decision, action_id, risk_score, matched_policies, warnings}`
- Responsibilities: Validate input, fetch org policies, compute risk, evaluate rules

**`app/api/actions/route.js`:**
- Triggers: Agent calls SDK `createAction()` or `updateOutcome()`
- GET: List actions with optional filters (agent_id, status, risk_min)
- POST: Create action record; validates against schema; generates embedding
- Responsibilities: Authorization, redaction, event publishing, quota enforcement

**`app/api/approvals/[actionId]/route.js`:**
- Triggers: Human reviews action and makes decision, or agent polls for approval
- POST: Record approval decision (allow/deny) + reasoning
- Responsibilities: Auth (admin only), state validation (action must be pending_approval), audit logging

**`app/api/signals/route.js`:**
- Triggers: On-demand via GET param `include_signals=true` or cron job
- Responsibilities: Compute 7 signal types; publish events; notify operators

**Page Entry Points (Frontend):**

**`app/decisions/page.js`:**
- URL: `/decisions`
- Purpose: Visual causal chain ledger of all governed actions
- Fetches: GET `/api/actions` with pagination/filtering
- Features: Timeline view, inline expansion, bulk deletion

**`app/approvals/page.js`:**
- URL: `/approvals`
- Purpose: Human-in-the-loop approval queue
- Fetches: GET `/api/actions?status=pending_approval`

**`app/mission-control/page.js`:**
- URL: `/mission-control`
- Purpose: Strategic posture + live decision stream + signal alerts
- Fetches: GET `/api/actions`, `/api/signals`, `/api/guard` history
- Real-time: WebSocket updates via `useRealtime()` hook

**`app/setup/page.js`:**
- URL: `/setup`
- Purpose: Readiness verification + instance health
- Fetches: GET `/api/health` (returns `readiness` status)

**`app/connect/page.js`:**
- URL: `/connect`
- Purpose: 8-minute onboarding to first governed action
- Shows: Copy-as-code SDK initialization + guard example

## Error Handling

**Strategy:** Fail fast; all errors logged with context; governance failures are explicit (not silent).

**Patterns:**

**Validation Errors:**
- Return 400 with `{error, details}` from `validateGuardInput()`, `validateActionRecord()`
- All input validated server-side; client input never trusted

**Guard Blocks:**
- Return 403 with `{decision: 'block', reason, matched_policies}`
- SDK throws `GuardBlockedError(decision)` on client; agent must handle

**Approval Denials:**
- Return 403 with `{decision: 'deny', reasoning}`
- SDK throws `ApprovalDeniedError(decision)` on client

**Authentication Failures:**
- Return 401 with `{error: 'Unauthorized'}`
- Checked via `getOrgId()`, `getOrgRole()`, `getUserId()` helpers

**Authorization Failures:**
- Return 403 with `{error: 'Admin access required'}`
- Role-based access control for sensitive operations (approvals, policy edit)

**Database Errors:**
- Catch in route handlers; return 500 with generic message
- Log full error to console with `[ROUTE-NAME]` prefix

**Error Logging Format:**
```
console.error('[GUARD] POST error:', err)
console.error('[ACTIONS] GET error:', err)
```

## Cross-Cutting Concerns

**Logging:** Console-based, prefixed with route name. No structured logging library (keeps stack minimal).

**Validation:** Hand-rolled schemas in `validate.js` (no external validators). Constraints: maxLength, enum, required, type.

**Authentication:** NextAuth session-based; middleware extracts from headers. Roles: `admin`, `member`, `viewer`.

**Authorization:** Role-based (admin-only for approvals, policy edit). Org scoping (all queries filter by orgId).

**Sensitive Data Redaction:** `scanSensitiveData()` identifies PII, secrets, credentials. Redacted in audit logs and responses.

**Event Publishing:** In-memory pub/sub via `publishOrgEvent()`. Subscribers: notification adapters, real-time updates.

**Quota Enforcement:** `checkQuotaFast()` validates org plan limits before action creation.

**Embeddings:** Vector generation for semantic action search; stored in `action_embeddings` table.
